# AI 架构方案：本地证据、LLM 与 Jev

版本：v1.0  
整理日期：2026 年 10 月 29 日  
状态：当前技术建议，尚未接入模型或实现原生清理引擎；具体供应商、部署方式与阈值待验证。

## 1. 当前取舍

首版建议采用 **本地扫描与规则引擎＋LLM＋受限原生执行器**，预留 Jev 接口。Jev 先进行旁路评测，只记录判断，不改变推荐或执行结果；验证收益后，再承担批量分类、排序与分流。

本文的 Jev 指 TypeSafe 的决策模型。它接收上下文与预定义问题，返回选项、评分或概率等结构化答案，适合边界明确的判断；LLM 负责调查疑难项目、理解用户意图、解释影响和生成总结。Jev 的接口特点可见 [官方介绍](https://docs.typesafe.ai/introduction)。

LLM 也能提供结构化输出。是否引入 Jev，应依据本产品的误判率、响应延迟、调用成本和维护成本评测，不能直接套用供应商的通用性能宣传。

## 2. 模块分工与工作流

| 模块 | 职责 | 输出 |
| --- | --- | --- |
| 本地扫描器 | 只读获取文件身份、软件归属、占用大小、进程占用及引用证据 | 有时间与版本标记的证据快照 |
| 规则引擎 | 校验范围、保护策略、权限、前置条件和允许的处理方式 | 可处理、待准备、待确认及原因 |
| Jev（可选） | 对已筛选上下文进行类别判断、复查排序和疑难分流 | 有限选项、分值及不确定性信息 |
| LLM | 请求补充检查、分析复杂关系、理解要求、解释影响及组织总结 | 引用证据的建议或补查请求 |
| 原生执行器 | 对已确认项目复查，执行隔离、恢复、删除并保存结果 | 逐项操作事件与失败原因 |
| 本地账本 | 保存选择、证据、确认、事件和空间读数，计算汇总 | 可追溯记录与确定性指标 |

```text
用户要求 → 本地只读扫描 → 规则检查
                           ├─ 证据明确：形成候选方案
                           └─ 需要判断：Jev 分流（可选）
                                          ├─ LLM 补充调查
                                          └─ 证据不足，待确认
候选方案 → 用户分项选择与确认 → 原生执行前复查 → 执行与记账
```

规则明确的项目无需逐文件调用模型。模型可请求受控的只读工具补充信息，程序返回检查结果后再分析；工具调用机制可参考 [LLM 工具调用文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。

## 3. Jev 的问题边界

将大问题拆成独立、明确的问题，交由代码组合结果。例如：

- 类别选择：缓存、日志、用户资料、运行组件、功能资源、未知。
- 证据判断：现有信息是否可能涉及用户资料，是否缺少归属依据？
- 分流选择：沿已验证规则处理、请求补充检查、交给 LLM 深查、待用户确认。
- 复查排序：哪些项目应优先核对影响范围？排序分值不代表允许删除。

不能用一次“这个目录可以删吗”概括归属、占用、依赖和用户需求，也不能让模型根据目录年龄或大小自行推导删除权限。

Jev 的 `confidence` 是由答案概率分布计算的指标，不能直接视为删除安全率。阈值须按问题和后果分别评测，高置信度也不能绕过本地验证与用户确认。[官方置信度说明](https://docs.typesafe.ai/confidence)

官方对 Jev 1.13 列出了数值计算、复杂间接推理和生成等局限；接入时应核对实际模型版本。大小求和、日期比较、空间差值始终由代码完成。[官方已知局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 4. 建议的接口契约

接口采用结构化对象，模型只能引用本地系统分配的项目与证据标识。

| 对象 | 关键字段 |
| --- | --- |
| `EvidenceSnapshot` | `snapshotId`、`itemId`、软件与规则版本、类别候选、大小口径、占用与引用检查、缺失信息、检查时间 |
| `DecisionRequest` | 证据摘要、用户意图、原子问题、允许选项、显式未知选项、规则约束 |
| `DecisionResult` | 项目标识、问题标识、分类或路由、不确定性信息、模型版本、请求标识 |
| `Advice` | 推荐操作、影响范围、前置条件、恢复限制、证据标识、规则或 AI 来源、待确认事项 |
| `ExecutionPlan` | 项目标识、证据快照、限定操作、确认范围与时间、待处理项目 |
| `ExecutionEvent` | 实际操作、时间、项目、实际数量与大小、成功或失败、原因、来源批次 |

模型提供的分类和建议仍须经过枚举、项目存在性、范围及状态校验。路径由执行器根据本地索引解析；不接收模型自由填写的路径、通配符或 shell 删除命令。

所有扫描类别都可加入方案，包括用户资料、运行组件和共享依赖。建议保留不等于禁止选择；已选择不等于可以立即执行。前置条件未满足的项目保持原状并保存为待处理计划，不进入隔离区、不计成功量。

执行前重新核对文件身份、路径边界、占用、引用与权限。确认范围或处理方式变化时，旧确认失效。普通文件默认先隔离；直接删除及涉及用户资料时，按产品方案进行必要确认。

## 5. 建议来源与可解释性

界面分别展示“规则已核实”“AI 辅助分析”“证据不足待确认”，避免仅以流畅文案表示可靠程度。一个项目可以同时有规则判断和 AI 解释。

每条建议保存证据标识、检查时间、规则版本、模型与提示模板版本、请求标识、用户选择及最终执行结果。后续复查追加记录，不能覆盖原判断和实际操作历史。

LLM 的说明应引用已取得的事实，区分观察结果与推断；不能把事后生成的解释冒充 Jev 的真实推理过程。无法确认归属、影响或恢复范围时，明确说明未知，并请求检查或保留为待确认。

清理总结先由账本计算删除量、隔离存量、恢复量和已复核磁盘净变化，LLM 只负责组织表达。不得生成容量、补造成功记录，或把同盘隔离量写成已释放空间。

## 6. 隐私与故障回退

- 本地优先。模型默认只接收必要的脱敏元数据、证据摘要和明确需要的规则片段；聊天正文、密码、令牌、备份内容不默认上传。
- 文件名、日志、文档和网页资料均作为待分析数据，不能作为改变权限或执行策略的指令。
- API 密钥使用平台安全存储，不写入仓库、提示词、日志或导出报告；接入云服务前核对其数据保留、部署和费用条件。
- 模型超时、网络失败、配额不足或结果无效时，已验证规则仍可提供基础能力；未知项维持保留或待处理，不静默采用更激进操作。
- Jev 与 LLM 判断冲突时补充证据或转待确认，不按任意一个高分直接执行。
- 原生执行结果才可更新文件状态。失败、跳过、中断和等待条件分别保存，不能根据模型回答“已完成”计账。

## 7. 评测与接入门槛

建立经人工核实、按软件和版本划分的测试集，覆盖可重建缓存、未同步资料、在用组件、共享依赖、旧版本仍被加载、中文路径、同名目录、权限不足和扫描后文件变化。保留独立测试集，避免调提示词与验收使用同一批样本。

比较规则基线、规则＋LLM、规则＋Jev、混合方案，记录分类质量、严重误推荐、拒绝判断与转待确认表现、补查效果、延迟、成本及失败回退。对未知项保守处理的覆盖率也要衡量，不能只追求自动推荐数量。

发布门槛建议：在高风险验收集中，用户资料、在用组件和共享依赖被误判为可清理缓存并加入推荐方案的次数为零；发现一次即阻止对应版本承担该自动推荐能力，修正后重测。该门槛只描述测试结果，不代表上线零风险。

固定并记录模型、规则和提示版本；更新任一版本后重跑关键用例。Jev 先旁路对照，再小范围承担分类与分流，保留关闭开关和上一稳定版本回退能力。

## 8. 演进顺序

1. 建立真实只读证据、规则与本地账本，先验证隔离恢复闭环。
2. 接入 LLM 的受控调查、影响说明和总结，检查每项建议能否追溯到证据。
3. 收集脱敏且经核实的评测样本，旁路比较 Jev 与现有方案。
4. 收益与风险达标后，逐步启用 Jev 批量分类和路由；执行权限仍由原生代码控制。

当前交互原型中的扫描、建议和操作仍为演示。本文是后续实现与评测依据，不表示已经接入 Jev、LLM 或具备真实清理能力。
